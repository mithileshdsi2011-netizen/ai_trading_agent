# Phase 9 — Security Audit Report

## Scope
Secrets, API keys, token storage, credential exposure, environment variables, unsafe logging, sensitive data in logs, path traversal, unsafe subprocess usage, and unsafe eval/exec.

## Summary
- **No eval/exec, subprocess, SQL, or path-traversal vulnerabilities found** in Python code.
- **Critical:** Kite access token is exposed in the token-server success page, and request tokens are written to `autostart.log` / `token_server.log`.
- **High:** Secret files (`.env`, `.envY`, `data/kite_token.json`) have world-readable `644` permissions.
- **High:** Kite API key is hardcoded in `dashboard.py` and `src/trading_orchestrator.py` instead of being loaded from configuration.
- **Medium:** `KITE_REQUEST_TOKEN` is stored in `.env` even though it is single-use and short-lived.
- **Low:** `/api/js-error` can log arbitrary browser messages, which could include sensitive data if the front-end ever stores tokens in the browser.

## Critical

### 1. Kite access token exposed in token-server HTML response
`get_kite_token.py` renders the fresh access token in the browser:

```@/Users/mithileshsinha/CascadeProjects/ai_trading_agent/get_kite_token.py:68-79
return f"""
...
<h3>Access Token (for reference):</h3>
<pre>{access_token}</pre>
...
"""
```

This exposes the token to browser extensions, screen captures, proxy logs, and shoulder surfing. The token is already saved to `data/kite_token.json`; there is no need to display it.

**Fix:** remove the access token from the HTML response. Return a generic success page.

---

### 2. Request token logged in autostart / token-server logs
The OAuth callback URL, including `request_token`, is logged by the embedded Flask development server:

```
logs/token_server.log:
127.0.0.1 - - [...] "GET /login?type=login&status=success&request_token=UgZrnSPNYfYvHYnRmdJE1fIAQoLZl49A&action=login HTTP/1.1" 200 -

logs/autostart.log:
127.0.0.1 - - [...] "GET /login?action=login&type=login&status=success&request_token=u178XYVyn08oIJ3ygCJDqW35b3Q79ufQ HTTP/1.1" 200 -
```

Request tokens are single-use and short-lived, but logging them violates least-privilege and creates an audit trail of credentials on disk. These logs are also unbounded in size.

**Fix:** disable Werkzeug request logging for the token server, or configure it to redact `request_token`.

## High

### 3. Secret files have world-readable permissions

```bash
-rw-r--r--  .env
-rw-r--r--  .envY
-rw-r--r--  data/kite_token.json
```

All three files are mode `644` (readable by any user on the machine). `.env` contains `OPENAI_API_KEY`, `KITE_API_SECRET`, `EMAIL_PASSWORD`, etc. `data/kite_token.json` contains the live Kite access token.

**Fix:**
```bash
chmod 600 .env .envY data/kite_token.json
```

And ensure startup scripts set this automatically.

## Medium

### 6. `KITE_REQUEST_TOKEN` stored in `.env`
Request tokens are generated by Kite during login and are valid for only a few minutes. Storing one in `.env` is misleading and unnecessary; the bot only needs `KITE_API_KEY`, `KITE_API_SECRET`, and the persisted access token in `data/kite_token.json`.

**Fix:** remove `KITE_REQUEST_TOKEN` from `.env` and `.env.example`.

### 7. Backup env file `.envY` contains real secrets
`.envY` is an unused backup copy of `.env` with the same credentials. It is gitignored but world-readable. It increases the attack surface.

**Fix:** delete `.envY` or restrict it to `600` and remove from the project.

### 8. Token expiry displayed in dashboard UI
`/api/data` returns `token_expiry`, and the dashboard shows it in the header and Bot Status tab. This is not a secret, but it is sensitive operational data.

**Risk:** low — an attacker who can read the dashboard already has significant access.

## Low

### 9. `/api/js-error` logs arbitrary browser messages
```@/Users/mithileshsinha/CascadeProjects/ai_trading_agent/dashboard.py:3710-3715
@app.route('/api/js-error', methods=['POST'])
def js_error():
    data = request.get_json(silent=True) or {}
    msg = data.get('message', 'unknown')
    stack = data.get('stack', '')
    app.logger.error('JS ERROR from browser: %s | stack: %s', msg, stack[:1000])
    return jsonify({'ok': True})
```

A malicious client could POST arbitrary content to this endpoint, which would be logged. If the front-end ever stores tokens in `localStorage`/`sessionStorage` and a JS error includes them, they would be logged on the server.

**Fix:**
- Sanitize / redact obvious patterns (tokens, passwords) from `msg` and `stack` before logging.
- Add a small rate limit per IP.
- Do not log the full stack in production unless debug mode is on.

### 10. No Content Security Policy or security headers
The dashboard HTML does not set `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, or `Referrer-Policy`. This is a minor hardening gap.

**Fix:** add security headers in the `index()` response.
